# Security scores

Each camera is rated on the **Local-Only Security Rubric v1**, defined in the Network Forensics plugin: [`skills/score-device-security/references/rubric.md`](https://github.com/danielrosehill/Network-Forensics-Plugin/blob/master/skills/score-device-security/references/rubric.md). It asks two questions, 50 points each:

- **Local-only viability (L1-L7):** cut off from the internet, does it keep working? RTSP/ONVIF to the NVR, the vendor app on the LAN, setup without the cloud, a cloud off switch, respect for LAN DNS/NTP, and degrading cleanly.
- **Cloud exposure (E1-E8):** while connected, what does it put at risk? Cleartext media, cleartext IDs, hard-coded DNS and IPs, how many clouds, idle media upload, weak local services, known CVEs, and an offline firmware path.

Every criterion carries an evidence level: `tested` (seen on our unit), `documented` (vendor or primary source, cited) or `inferred` (reasoning stated). A `fail` always rests on tested or documented evidence. Red flags cap the grade: cleartext media off the LAN caps it at D, and losing local streams when blocked means F. Untested criteria score 0 and keep the grade **provisional**, shown with its ceiling (the grade if everything untested passes).

The source of truth is [`scores/*.json`](scores/). The tables below are generated by the plugin's `scripts/score.py`:

```bash
python3 <Network-Forensics-Plugin>/skills/score-device-security/scripts/score.py --table scores/*.json
```

## Re-scoring

After a device is blocked and verified (plugin skill `verify-iot-lockdown`, which writes `forensics/<date>-<model>/post-block.md`), update its JSON (L1, L2, L4, L5, L7 become `tested`), bump `assessed`, regenerate these tables and update the README.
